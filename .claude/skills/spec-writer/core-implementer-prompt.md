# Core implementer prompt

The prompt for an engine core session (#1207): the module prompt of [`implementer-prompt.md`](implementer-prompt.md), changed for a core. A core is one native program judged by the core gate, not a WebAssembly module judged by the module gate, and it is submitted with the wind_meteors module it hosts. Replace `<groups left out>` with the groups the session is not judged on and why (for #1207's first sessions: `files`, whose loader is the Nanolathe port, ozgb/btm#31, not yet merged), or with `none`.

```text
You are implementing the engine core of a game engine, in Rust, from a behavioural specification. Work only from what is in this machine: the contract at /work/specs/engine-core.md, the scaffolding at /work/specs/engine-core-transition.md (and /work/specs/TEMPLATE.md), and the data kit at /data (read /data/README.md first; /data/docs/core-gate.md is how a core is run and judged, and the form of a core; /data/reference/core/ holds the gate's inputs; /data/docs/module-abi.md is the module ABI the core hosts modules by; /data/docs/trace-format.md the trace and its hash; /data/docs/sim-events.md the sim event queue; /data/docs/commands.md the commands and console lines; /data/runtime/vectors/README.md the runtime entries; /data/interfaces/ the interface headers). Do not try to find the original game's code or any other implementation of it.

Goal: a core that the core gate judges `equal` on every group but these, which this session is not judged on: <groups left out>. The result still lists those groups; ignore their status.

Rules:
- The core is one program: a statically linked (musl) x86_64 Linux executable that answers `CORE GROUP CALLS OUT` as /data/docs/core-gate.md states, one run per vector. Check that it is static (`file` or `readelf -d` shows no dynamic section and no interpreter) before submitting.
- Write the crate under /work/core/. Use only crates you need from crates.io (a WebAssembly runtime for hosting modules is one you may need); record why each is there in the notes. Build in this machine.
- The core hosts the wind_meteors module of /work/wind_meteors/, built in this machine with its own /work/wind_meteors/build.sh. Do not change /work/wind_meteors/ or /work/specs/.
- Submit through the mailbox: for request id N (req1, req2, ...), write /srv/outbox/reqN/core (the executable) and /srv/outbox/reqN/module.wasm (the wind_meteors module), then create /srv/outbox/reqN/ready. Do not write a `subsystem` file: that makes it a module request. The verdict appears in /srv/inbox/reqN.json, with a status per group and per vector; poll for it. Test each group yourself before you submit: /data/reference/core/<group>.json holds each vector's calls and results, and /data/runtime/vectors/ the runtime records, so a harness of your own can compare every line. A full gate run takes a long time and names only the first call that differs in each vector.
- When a verdict says a vector differs or failed, find the cause from the verdict's fields, the specs and the kit, fix it and submit again. If you conclude a spec is wrong, missing something, or contradicts the kit, do not guess: write the question and your evidence to /work/core/SPEC-QUESTIONS.md and continue with anything else you can.
- Commit source only: add `target/` and every built file (`*.wasm`, the core executable) to /work/.gitignore before your first commit, and keep every built file out of every commit. Never commit /work/.review/.
- Commit on a branch named `impl/engine-core` in /work. Commit messages are `<Type>: <Subject>` (Type one of Add, Fix, Update, Docs; imperative subject of at most 50 characters), ending with a blank line and `Assisted-by: Claude Code:<your model id>`.
- Hand the branch over whenever you have a verdict better than the last one you handed over, and at the end: `git bundle create /srv/outbox/.btm.tmp impl/engine-core && mv /srv/outbox/.btm.tmp /srv/outbox/btm.bundle`. If /srv/inbox/push.json says a push was refused, rewrite the branch so that no commit holds the file it names, and hand it over again.
- At the end, write /work/core/IMPLEMENTATION-NOTES.md (committed): what you built, the crates and why, the verdicts you got in order (per group), and every place the specs or the kit were unclear.
```
